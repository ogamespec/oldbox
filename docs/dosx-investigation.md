# DOSX standard-mode fault: current evidence

Состояние на текущем этапе.  Цель — не «залечить» гостя, а найти причину в
эмуляторе.

## Воспроизведение

`freedos-win95.img` → `A:\>` → `D:` → `SETUP`.  Один Enter на приглашении
«To continue, press ENTER»; повторных запусков SETUP нет.  На чистом
`win95-hdd.img` ошибка возникает до копирования файлов:

```
Standard Mode: Fault outside of MS-DOS Extender.
EC=0000 CS=0387 IP=2AC0 AX=0001 BX=0000 CX=0000 DX=FFFF
SI=0002 DI=00FC BP=0000 DS=0397 ES=039F SS=027F SP=0FE0
```

## Что проверено

Снято состояние непосредственно перед входом в `0387:0B7E`.

- `CS=0387`: base `0x0040DE20`, limit `0x02ABF`, access `FB`, flags `10`
  (16-битный код).
- Блок `0x0040DE20..0x0040E8DF` полностью нулевой.
- По адресу `0x0030DE20` (другой блок, не алиас A20) лежит валидный
  16-битный код; на `+0x0B7E` он читается как осмысленные инструкции.
- A20 здесь ни при чём: `0x40DE20` не содержит бита 20, поэтому A20-off
  не превращает его в `0x30DE20`.  Проверка с принудительным A20=off это
  подтвердила.
- Дескриптор в LDT (base `0x31DC50`, selector `0x0387`, offset `0x380`):

  ```
  bf 2a 20 de 40 fb 10 00
  base  = 0x0040DE20
  limit = 0x02ABF
  ```

- Если вручную скопировать `0x30DE20..` в `0x40DE20` непосредственно перед
  входом, код начинает исполняться, но падает на `0387:0BB4` (`STOSD` в
  `ES:EDI`, EDI=`0x377F`) с `#GP(0x384)`: это за пределами лимита
  `0x2ABF`.  То есть простая «пропущенная копия» не объясняет картину —
  содержимое и/или дескриптор не согласованы.

## Что это исключает

- HIMEM/размер RAM/частота CPU — ошибка детерминирована и локальна.
- A20 — адрес `0x40DE20` не пересекается с `0x30DE20` по линии A20.
- «Повторный SETUP после перезагрузки» — ошибка воспроизводится с одним
  Enter и до копирования файлов на HDD.

## Откуда берётся блок 0x40DE20

Watchpoint по таблице `0x32F230..0x32F250` показал, что она заполняется в
`037F:28E4` (запись base `0x40DE20`) сразу после `INT 31 AX=0501`
(DPMI Allocate Memory Block, `037F:284D`, `CX=0x2000`).  Затем код
`037F:28B6..28C5` инициализирует в блоке связный список 256 записей по
32 байта (`037F:28F9`).  То есть `0x40DE20` — это **DPMI-блок памяти
DOSX**, а не образ файла и не копия `0x30DE20`.

Селектор `0387` с base `0x40DE20` указывает на этот блок; код по
`0387:0B7E` ожидает там исполняемый код, но блок остаётся нулевым.  Почему
именно этот блок назначен кодовым сегментом — следующий вопрос.

## Разрез блока 0x30DE20

В `037F:3CF3..3D48` найден код, который делит существующий блок:

```
ebx = [esi+0x0C] - edx      ; остаток
eax = [esi+0x08] + edx      ; база остатка
...
[eax+0x0C] = ebx            ; размер остатка
[esi+0x0C] = edx            ; размер выделенной части
edx = eax                   ; вернуть остаток
```

При наблюдении за таблицей получилось:

```
исходный блок: base 0x30DE20, code/data ~0x12AC0
edx (смещение разреза) = 0x100000
остаток: base 0x40DE20, size 0x2AC0
```

То есть `0x40DE20` — **остаток после разреза блока по смещению 1 МиБ**, а
не образ кода.  Код KRNL386/обработчика остаётся в исходном блоке
`0x30DE20`; селектор `0387` почему-то получает базу остатка `0x40DE20`.
Это объясняет и `limit=0x2ABF`: у остатка размер `0x2AC0`, а полный блок
имеет `0x12AC0`.

Проверка «скопировать полный блок `0x12AC0` и выставить лимит `0x12ABF`»
выполнена: исходное падение `0387:0B7E` с `#GP(0x394)` остаётся, потому что
код в `0x30DE20` не предназначен для текущих DS/ES, а после обработчика
появляется новое падение `0070:12B1` (`#GP(0x2DC)`).  Значит, низкий блок
не является готовым кодом для `0387`; простая замена base/limit не решает.

Сам дескриптор `0387` записывается через DPMI Set Descriptor в
`037F:2B77`: в LDT по `0x31DFD0` уходят байты `BF 2A 20 DE 40 FB 10 00`
(base `0x40DE20`, limit `0x2ABF`, 16-битный код).  То есть ошибочная база
попадает в LDT именно на этом вызове; источник байтов — входной
дескриптор `ES:DI` вызывающего кода.

## MS-DOS 7 и HDD

Исходный `win95-hdd.img` был размечен с CHS-геометрией 255 головок, а Award
BIOS работает с LBA; MS-DOS 7 Setup/ScanDisk отказывался продолжать
(«suspect partition»).  `tools/make_win95_hdd.py` теперь помечает раздел
типом `0x0E` (LBA).  После этого MS-DOS 7 Setup проходит ScanDisk и доходит
до того же DOSX-падения, но с `CS=036F`, `IP=2AC0` (селектор отличается от
FreeDOS-варианта `0387`, смещение и нулевой блок те же).

Это доказывает, что падение не зависит от FreeDOS: оно воспроизводится и на
MS-DOS 7.  HDD-разметка была отдельным блокером, но не причиной DOSX.

## IFSHLP

Добавление `DEVICE=IFSHLP.SYS` из `DOS Drivers.zip` в FreeDOS-дискету не
помогло: падение то же, `0387:2AC0`.

## EMM386

Проверен вариант с Microsoft EMM386 4.44 (`DEVICE=EMM386.EXE NOEMS`).
В oldbox он падает ещё до SETUP: `IDT gate 22 not present` и shutdown.
То есть EMM386-путь сейчас не является обходом и, возможно, указывает на
ту же проблему V86/IDT, что и DOSX.

## Разбор DOSX.EXE

`DOSX.EXE` (32682 байта) лежит в `MINI.CAB` на установочном ISO и упакован
Microsoft EXEPACK; точка входа — распаковщик.  В гостевой памяти DOSX уже
распакован, его код начинается с `CS base 0x4E320`.

В распакованном образе найдена таблица по `0x32F238`:

```
20 de 40 00   base = 0x0040DE20
c0 2a 00 00   size = 0x00002AC0
```

То есть блок `0x40DE20` длиной `0x2AC0` — это отдельная запись, а не
результат копирования `0x30DE20`.  При этом сразу за блоком, по
`0x4108E0 = 0x40DE20 + 0x12AC0`, в дампе есть ненулевые данные, а
`0x12ABF` отличается от фактического лимита `0x2ABF` только старшим
нибблом.  Это может быть признаком потери старших 4 бит размера/лимита,
но подтверждения в коде пока нет.

## Следующий шаг

Найти, кто и из какого источника должен заполнять блок `0x40DE20`:
трассировать создание дескриптора `0x387` (LDT `0x31DC50`, offset `0x380`)
и вызовы, которые создают/копируют блок.  Снимок перед входом:
`--break 0387 --break-save FILE` (см. `docs/state.md`).
